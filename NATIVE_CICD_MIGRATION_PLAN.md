# Native CI/CD migration plan

## Implementation status

The four reviewed native source trees are integrated into `native/`. The `native` workflow supplies pull-request checks and unpublished trial artifacts; the existing release and TestFlight workflows are wired to native builds. These new workflow paths have not yet run on GitHub Actions with production signing credentials, and must not be treated as validated release automation until that happens. Existing release workflow names and run-number streams are retained, but store-side monotonicity and signing identities must still be checked. No production release has been published.

With no physical devices available, simulator and container checks are the available evidence; physical delivery, device keychains and accessibility remain unverified. An initially empty server database does not prevent a later in-flight registration from racing removal.

## Version and build-number contract

- Keep one release-please-managed marketing version in sync with the server, all native artifacts, tag and changelog. Currently `release-please-config.json` updates `server/mix.exs`, `mobile/pubspec.yaml` and README, and `release.yml` checks the tag against server and Flutter versions. Choose a release-please-managed repository version source before removing Flutter; update all native generators and scripts and the version job together. During transition, keep the existing Flutter version source until the replacement is wired and verified. Never hand-edit release-please-managed versions.
- Preserve monotonically increasing Android `versionCode` and Apple build numbers across the existing workflows and prior releases. `github.run_number` is scoped to a workflow, so splitting or renaming workflows can reset it. Establish and verify a continuity mechanism against the latest Play and App Store Connect build numbers before cutover; fail on missing or non-increasing values. Pass Android `-PversionCode` and `-PversionName`, iOS `CURRENT_PROJECT_VERSION` and `MARKETING_VERSION` consistently to app and extension, and macOS `PUX_BUILD_NUMBER` and marketing version. Verify the packaged metadata, not just build inputs.
- Retain conventional commits and release-please's draft-release, changelog and tag behavior. Update version checks and extra-files as one reviewed migration; avoid silently producing native artifacts with build number 1.

## Pull-request checks

1. Extend the current `mobile` change filter to include each `native/<platform>/**`, shared native fixtures and relevant workflow/toolchain files. Preserve an always-reported required aggregate check (currently `mobile-ok`), including correct failure and cancellation handling and fork PR operation without secrets. During transition run Flutter checks for Flutter changes and native checks for native changes; do not silently skip cross-platform protocol fixture changes.
2. Pin supported toolchains and dependencies in `mise.toml` or versioned build configuration and pin Actions by commit as the existing workflows do. Keep caches keyed by lockfiles and toolchain versions. Add lint, formatting, unit tests and unsigned builds per platform:
   - **Android:** JDK 21 and pinned Android SDK/Gradle; unit tests, lint, debug APK and unsigned or test-key release build. Verify manifest, version injection and signing with a disposable key. Keep production credentials unavailable to PRs.
   - **iOS:** pinned Xcode and simulator; Swift tests plus `xcodebuild` app and extension build and simulator tests. Verify generated project consistency, target versions, development versus production APNs entitlements and matching app/extension identifiers. Use ad-hoc signing where practical without distribution secrets.
   - **macOS:** run `native/macos/scripts/test.sh` and a universal bundle build. Check both architecture slices, minimum deployment metadata, embedded libsodium and rpaths. Run a safe non-production Keychain probe where the runner permits it and report an explicit skip otherwise; do not test against the production service.
   - **Linux:** build on Ubuntu 22.04 x86-64, with pinned compiler/CMake, GTK 3, libsecret, curl, libsodium and packaging/test dependencies. Run the suite under Xvfb and an isolated D-Bus/GNOME Keyring session with `PUX_REQUIRE_KEYRING=1`, fail on skipped keyring tests, bound external processes and preserve logs. Build and install/uninstall the `.deb` in an isolated environment, smoke-test the tarball and check dependencies and minimum glibc. Add arm64 coverage where available; the Opus container run was arm64, not the released amd64 target.
3. Add cross-client tests against the existing server fixtures and a disposable server: sealed-box interoperability, enrollment exchange, registration, notification and reconnect/ack behavior. Include removal and crash-recovery cases without relying on production services or credentials. Record which checks are simulated, simulator-based or physical-device tests.

## Release and distribution

1. Add a manual, non-publishing native trial workflow first. Build and retain artifacts for inspection, exercise signing only with appropriately scoped secrets on trusted events, and verify bundle/package contents and checksums. Keep PR jobs secret-free. Verify Firebase configuration is explicit and fails visibly when absent; do not log tokens or private data.
2. Replace Android release commands with native Gradle APK and AAB builds, using the existing upload keystore secrets and package identity. Verify signature continuity against the installed Flutter release, version metadata and both artifacts before enabling the existing optional Play upload. Clean temporary signing material even on failure.
3. Replace iOS TestFlight archive/export with the native Xcode project and scheme. Preserve serialization of uploads, monotonic build numbers, app and extension profiles, production APNs entitlement, Keychain group, API-key handling and cleanup. Validate a signed archive and physical-device upgrade and push before enabling upload.
4. Replace the macOS release build with the native universal bundle, existing Developer ID/profile, Keychain access probe, hardened runtime, notarization, stapling, Gatekeeper checks and DMG packaging. Confirm both architecture slices and embedded libraries after signing and relocation; test an actual signed upgrade, Intel and macOS 12 where available.
5. Replace the Linux release build with native Ubuntu 22.04 amd64 artifacts using `native/linux/packaging/build_deb.sh` and `build_tar.sh`, retaining published filenames and checksums. Verify package dependencies, install/uninstall, keyring migration and desktop notifications on supported distributions. Preserve server image builds and release notes/publish dependencies.
6. Run old and native builds side by side as unpublished workflow artifacts until signed upgrade, live delivery and rollback checks pass. Switch each release job only after its acceptance evidence is reviewed. Keep the existing release and TestFlight workflow names or deliberately address build-number continuity and required-check settings; never change organization settings as part of this work. Publish native artifacts only through the normal authorized release process.

## Cutover verification and rollback

- Exercise a signed in-place Flutter-to-native upgrade for Android and iOS, including existing enrollment, device ID, protected storage, notifications, background delivery and deletion/recovery. Verify Firebase/APNs and iOS extension decryption on hardware. Confirm camera, clipboard and notification actions with the OS restrictions in effect.
- Verify signed macOS Keychain migration, launch-at-login, menu bar, held-code recovery and notification permissions on supported versions and architectures. Verify Linux real Secret Service migration, locked/corrupt recovery, notifications and reconnect against the deployed server on supported desktops and amd64. Inspect representative setup, enrolled, error and recovery screens in light/dark, large text and with platform screen readers.
- Test release artifacts from a clean machine, including upgrades, offline/reconnect and a rollback to the previous version. Define a supported recovery path if a downgrade cannot read migrated storage. Preserve prior release artifacts and never silently replace an enrollment after migration failure.
- After all four native targets pass and the rollout is stable, remove Flutter-specific CI, packaging and toolchains in a separate reviewed change. Update README, contributor instructions, platform release documentation and required checks together. Keep unresolved server-fence and hardware-verification limitations visible until closed.
