# Play Data Safety and App Store privacy labels

Answers for the two forms, for the hosted service at pux.vidur.xyz, with the reason for each. They have to agree with the [privacy policy](../server/lib/pux_web/controllers/page_html/privacy.html.heex); if the code or the policy changes, check these again. The references are to the code as of this writing.

## What actually leaves the device

| Data | Sent by | Kept on the server | Where in the code |
|------|---------|--------------------|-------------------|
| Public key | App, `POST /records` | In `records` until the relay is deleted, or 30 days after it loses its last device | `Pux.Records.create_record/1`, `Pux.Records.Record` |
| Record ID, inbox token | Generated by the server and returned to the app; the record ID comes back as the bearer token on every request | Same as the public key | `Pux.Records.Record`, `PuxWeb.Plugs.RecordAuth` |
| FCM push token, platform (`fcm` or `desktop`) | App, `POST /record/devices`, on every start and token refresh | In `devices` until removed, reported dead by FCM, or 2 years without a registration or accepted push | `PushService._register`, `Pux.Records.Device`, `Pux.Workers.PruneWorker` |
| Timestamps: relay created and last active; device registered, last seen and last checked | Set by the server when the app registers and when a push is accepted | With the row they belong to | `Record.last_active_at`, `Device.last_seen_at`, `Device.token_checked_at` |
| Firebase installation ID | The Firebase Messaging SDK, to Google | Not on our server | the native Firebase SDKs |
| Device ID | Generated by the server per registration and stored by the app | With the device | `DeviceController.create/2` |
| IP address | Every request | In memory for rate limiting; logged only when the relay-creation limit is hit | `PuxWeb.Plugs.RateLimit` |

What reaches the server without passing through the app:

| Data | From | Kept | Where |
|------|------|------|-------|
| Forwarded email | The user's email provider, over SMTP | Not stored. Parsed in memory; a message with no code is dropped | `Pux.Inbound.classify/3`, `Pux.SMTP.Session` |
| Sealed payload (code, sender, DKIM result, time) | Built from the email and sealed with the relay's public key before it's stored | Push jobs about 10 minutes after they finish; desktop copies until acknowledged or about 15 minutes | `Pux.Push.deliver_to_record/2`, `Pux.Crypto.seal/2`; Oban's `Pruner` (`max_age: 600`) and `Pux.Workers.PruneWorker` |

Nothing else: no name, email address, phone number, contacts, location, photos, analytics or crash reports. Camera frames from the QR scanner stay on the device (no upload). The native app dependencies are in the platform build files; none is an analytics, advertising or crash-reporting SDK.

## Google Play: Data Safety

### Overview

| Question | Answer | Why |
|----------|--------|-----|
| Does your app collect or share any of the required user data types? | Yes | The push token and identifiers below leave the device |
| Is all of the user data collected by your app encrypted in transit? | Yes | The app only talks to an `https` server (an imported or scanned enrollment may use plain `http` only for `localhost`, `127.0.0.1` and `10.0.2.2`, for development), production sets HSTS (`server/config/prod.exs`), and Firebase uses TLS |
| Do you provide a way for users to request that their data is deleted? | Yes | **Delete relay everywhere** and **Remove this device** in the app; or by email to `privacy@vidur.xyz` |

Play asks apps that let users create an account to give a web link for deletion requests too. A relay is not a sign-in account, but if Play treats it as one, use `https://pux.vidur.xyz/privacy` (see the notes at the end).

### Data types

Declare these and leave everything else unticked.

| Category: type | Collected | Shared | Processed ephemerally | Required or optional | Purposes | Why |
|----------------|-----------|--------|-----------------------|---------------------|----------|-----|
| Device or other IDs | Yes | No | No | Required | App functionality | FCM push token, Firebase installation ID, the server's device ID, the record ID and inbox token. They identify the app install and relay, not a person, so they aren't Personal info: User IDs |
| App activity: Other actions | Yes | No | No | Required | App functionality | The device's last-seen time is when the app last registered (on each start) or a push was accepted, and it decides when an idle device is deleted. It's a single timestamp, not a log of interactions |
| Messages: Emails | Yes | No | Yes | Required | App functionality | The forwarded bank emails are read in memory to find the code and never stored. They arrive from the user's email provider rather than from the app, so this is arguably not "collected by the app", but the service exists to read them, and declaring it matches the policy |

Not shared: Google (FCM) delivers pushes as a service provider acting for us, which Play doesn't count as sharing. Nothing is sold or used for advertising.

Not declared, and why:

- **The OTP itself and the payload around it.** It's sealed with libsodium for the user's devices before it's stored or sent, and the server can't open it; Play exempts end-to-end encrypted data.
- **The public key.** Not a Play data type and not personal: it can only encrypt to the device.
- **IP address.** Play has no IP type and only counts it where it's used to work out location. pux uses it in memory for rate limiting and never derives a location.
- **Camera.** Frames are decoded on the device and never leave it.
- **Email to privacy@vidur.xyz.** Sent outside the app.

## App Store: privacy nutrition labels

Apple counts data as collected when it leaves the device and can be read for longer than it takes to serve the request. So the forwarded emails, which are never transmitted by the app and are held only while being parsed, are not collected, and nor are sealed payloads, which only the user's devices can open.

**Data used to track you:** none. pux has no tracking, no advertising and no data brokers, so no App Tracking Transparency prompt.

**Data linked to you:** the items below. They aren't tied to a name or email address, but they are tied to each other through the relay, and Apple treats anything not de-identified before collection as linked.

| Apple category: type | Purposes | Linked | Tracking | Why |
|----------------------|----------|--------|----------|-----|
| Identifiers: Device ID | App Functionality | Yes | No | The FCM push token and the Firebase installation ID that the Firebase SDK sends to Google; the server's device ID |
| Identifiers: User ID | App Functionality | Yes | No | The record ID, which works like an assigned account ID, and the inbox token. Apple's definition covers "assigned user ID" |
| Usage Data: Product Interaction | App Functionality | Yes | No | The device's last-seen time records the last app start or accepted push, and is used to delete idle devices |

**Data not collected:** contact info, health, financial info, location, sensitive info, contacts, user content (emails, codes and photos stay unreadable to us or on the device), browsing and search history, purchases, diagnostics, other data.

The App Store asks for a privacy policy URL: `https://pux.vidur.xyz/privacy`.

## Notes and open questions

- **Web deletion link.** The policy says how to delete in the app and by email, but has no stable anchor for Play's deletion URL field. If Play asks for one, link `https://pux.vidur.xyz/privacy` and consider adding an `id` to the "Your choices" heading.
- **Encryption in transit.** The policy doesn't mention HTTPS at all, while the Play answer relies on it. Inbound SMTP from email providers is only encrypted when the server has `SMTP_TLS_CERTFILE` and `SMTP_TLS_KEYFILE`; check that the hosted instance has them before relying on it in any copy. (That mail doesn't come from the app, so it doesn't change the Play answer.)
- **Firebase.** The policy names Firebase and its installation identifier. The Android Firebase Messaging SDK can also report message delivery data to Google; check what the current SDK sends before submitting, and declare it under Device or other IDs if it adds anything.
- **Age.** The policy requires users to be 18. Set the store age ratings and Play's target audience to match (18+), even though the content itself would rate lower.
